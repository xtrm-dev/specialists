# XTRM-93 N3 lane T8 — Prometheus, OpenTelemetry, and live aggregates

**Tree audited:** `feature/xtrm-93-n0n2-recon` at `553b5a23`. **Metric-family count:** 23 declared families: 15 table/snapshot-derived and 8 forensic-event-derived. The production collectors pass only statuses and job metrics, so all 8 forensic-event families are unreachable from both shipped exporters (`src/specialist/prometheus-projection.ts:84-95,233-245,456-477`).

## 1. Real observability integrations

`observability.db` is not the whole live-observability system:

- The Prometheus projection reads `listStatuses()` and `listJobMetrics()` from the SQLite client (`src/specialist/prometheus-projection.ts:75-95`). It does **not** read forensic events (`src/specialist/prometheus-projection.ts:84-95`).
- `sp console` builds its live snapshot from a reconciliation of SQLite statuses and per-job `status.json`, selecting the newer same-ID record (`src/cli/console/runtime.ts:953-972`), then calls the pure scalar aggregator (`src/cli/console/runtime.ts:235-267`).
- The native host also exposes per-activation live stats directly from its in-memory registry, not SQLite (`src/activation/native-host.ts:2605-2624`; `src/activation/types.ts:226-240`).
- Native session/lifecycle events are adapted into the shared timeline and forensic SQLite writers (`src/activation/forensic-sink.ts:1-15,165-177,253-290`). Legacy jobs additionally retain `events.jsonl`, `status.json`, and `result.txt` semantics (`src/specialist/timeline-events.ts:54-58`).

## 3. Cardinality safeguards and failures

1. **Key allowlist:** only the exact keys in `DEFAULT_LABEL_ALLOWLIST` can survive `safeLabels`; opaque IDs and secret/payload keys are explicitly forbidden (`src/specialist/forensic-events.ts:158-240`; `src/specialist/prometheus-projection.ts:744-748`). The validator also rejects forbidden **key names** in rendered text (`src/specialist/prometheus-projection.ts:248-271`).
2. **The protection checks keys, not values.** `pickAllowedLabels` stringifies allowed values without detecting an activation ID carried under an allowed key (`src/specialist/forensic-events.ts:436-450`). Therefore an activation ID leaked into any free-form allowed dimension is catastrophic: especially `repo`, `participant_role`, `model`, `model_provider`, `tool_name`, `chain_template`, `mcp_server`, `mcp_method`, `gate_kind`, `evidence_kind`, `credential_kind`, `policy_kind`, `action_kind`, `eval_kind`, `severity`, or `state` (`src/specialist/forensic-events.ts:204-240`). Fixed dimensions (`service_name`, `participant_kind`, `process_kind`) and finite classifier outputs are safe only while their producers remain fixed (`src/specialist/prometheus-projection.ts:27-30,309-315,618-621,636-660`).
3. **Exact normalization ceilings:** `chain_template` and generic forensic kinds normalize to `[a-z0-9_.:-]` and fall back to `unknown` when empty or **over 80 characters** (`src/specialist/prometheus-projection.ts:303-307,673-677`); model falls back to `other` only when **over 80 characters** (`src/specialist/prometheus-projection.ts:819-823`); tool name falls back to `other` when empty or **over 60 characters** (`src/specialist/prometheus-projection.ts:832-836`). These are length ceilings, not cardinality ceilings.
4. **No global series-count ceiling exists.** `normalizeState` has no length ceiling, and `modelProviderFor` has neither a value-count nor length ceiling (`src/specialist/prometheus-projection.ts:815-829`). `repo` and `participant_role` are passed raw (`src/specialist/prometheus-projection.ts:331-375`).
5. **Fallbacks:** missing/blank chain template becomes literal `chain`; an invalid/overlong supplied template becomes `unknown` (`src/specialist/prometheus-projection.ts:289-306`). Missing normalized kinds become `unknown`; missing model/provider labels are omitted; missing state becomes `unknown` (`src/specialist/prometheus-projection.ts:331-375,673-677,815-829`).
6. **Histogram multiplication:** every distinct base tuple creates 13 job/chain bucket series plus `_sum`/`_count`, or 11 wait buckets plus `_sum`/`_count` (`src/specialist/prometheus-projection.ts:24-26,726-741`). A leaked activation ID therefore multiplies the damage by 15 or 13 series per histogram family.

## 4. OpenTelemetry verdict

**ABSENT as an OpenTelemetry integration.** `package.json` has no OpenTelemetry API, SDK, exporter, or instrumentation dependency (`package.json:100-117`). The source has no `OTEL_*` configuration, tracer construction, span lifecycle, context propagation API, OTLP exporter, or collector endpoint; this is a verified negative direct grep, so there is no positive `file:line` to cite.

What exists is local correlation/schema vocabulary, not OTel runtime instrumentation:

- MCP request `traceId` and `spanId` are random UUIDs minted in-process (`src/mcp/request-meta.ts:5-31`; legacy MCP server equivalent `src/server.ts:52-75`).
- Forensic envelopes permit an arbitrary `otel` record (`src/specialist/forensic-events.ts:140-156,242-259`).
- Only MCP timeline events synthesize a small semantic-attribute object (`mcp.method.name`, `mcp.session.id`, `jsonrpc.request.id`, `network.transport`, `gen_ai.operation.name`, `gen_ai.tool.name`) (`src/specialist/forensic-events.ts:800-810`).

No span is started, ended, sampled, or exported by those fields. Calling this tree “OpenTelemetry-enabled” would be incorrect.

## 7. Mixed-fleet hazards, with arithmetic

### Critical — token counter is currently shape-broken; the requested basis premise does not hold in current persisted rows

The shared job-metric writer stores both `turn_summary` and `token_usage` trajectory entries as `{..., token_usage: {...}}` (`src/specialist/observability-sqlite.ts:2909-2918`). The Prometheus reader looks only for flat fields such as `latest.input_tokens` and `latest.total_tokens` (`src/specialist/prometheus-projection.ts:434-453`). Consequently, freshly aggregated legacy **and native** records normally yield no `xtrm_llm_tokens_total` sample. The unit fixture bypasses the real writer and supplies a flat object (`tests/unit/specialist/prometheus-projection.test.ts:7-33,76-108`).

The audit premise “last trajectory element is per-turn for legacy and session-cumulative for native” is therefore **not verified for the actual `specialist_job_metrics` rows**. Native cumulative usage exists in status/in-memory state: the native sink calls `accumulateTokenUsage` and stores the result in `state.tokenUsage` (`src/activation/forensic-sink.ts:279-290`), while legacy status merges the latest per-event keys over prior keys rather than summing (`src/specialist/supervisor.ts:1455-1464`). But the cumulative native status value is not copied into the token trajectory consumed by Prometheus (`src/specialist/observability-sqlite.ts:2909-2918`).

Arithmetic error now: for desired token total `T`, the exporter reports `0` for newly derived nested rows, so error is `−T`. If a compatibility adapter flattens historical rows but preserves a legacy last-turn value `L_j` and native session cumulative `C_k`, observed increase is `ΣL_j + ΣC_k`; desired is `Σ(Σ_t tokens_{j,t}) + ΣC_k`; undercount is `−Σ_j Σ_{t<last} tokens_{j,t}`. Summing `rate(xtrm_llm_tokens_total)` across a mixed fleet therefore combines zero/new rows, legacy last-turn rows, and native cumulative rows unless the record contract is versioned.

### Critical — dual-running status rows double-count jobs and processes

Both gauges count every status row with no logical-activation deduplication (`src/specialist/prometheus-projection.ts:103-131`). Legacy writes status rows through the supervisor (`src/specialist/supervisor.ts:1535-1542,2777-2799`); native writes separate activation-ID status rows through the forensic sink (`src/activation/forensic-sink.ts:96-126,165-177`). If dual running creates two rows for one logical activation, `sum(xtrm_job_state)` and `sum(xtrm_processes)` report `2` instead of `1`: error `+1` per duplicated activation, up to 100% inflation when every job is duplicated. `rate()` is not meaningful for these gauges; a scraper that applies it additionally interprets lifecycle transitions as counter deltas.

### High — native turns count assistant messages, legacy turns count `turn_end`

Legacy emits one `turn_summary` from each RPC `turn_end` (`src/pi/session.ts:1394-1411`; `src/specialist/supervisor.ts:2353-2373`). Native emits one `turn_summary` from each assistant `message_end` (`src/specialist/native-activation-observability.ts:342-354`), while the native live counter separately increments on `turn_start` (`src/activation/forensic-sink.ts:264-270`). The common writer increments `total_turns` for every `turn_summary` (`src/specialist/observability-sqlite.ts:2909-2913`). Thus a native turn with `m` assistant messages contributes `m`, while a legacy turn contributes 1. Mixed observed rate is `legacy_turn_rate + native_assistant_message_rate`; desired completed-turn rate is `legacy_turn_rate + native_turn_rate`; overcount is `native_assistant_message_rate − native_turn_rate = Σ(m−1)/time`.

### High — native resume remains “waiting” in the job-metric phase machine

The metric writer changes phases only on `run_start` and `status_change` events and closes time into `active_runtime_ms` or `waiting_ms` (`src/specialist/observability-sqlite.ts:2885-2898,2921-2950`). Legacy resume explicitly emits `status_change(running)` (`src/specialist/supervisor.ts:1858-1866`). Native `activation_resumed` is declared to have no timeline counterpart (`src/specialist/native-activation-observability.ts:50-72`), and a native `turn_start` maps only to a turn boundary (`src/specialist/native-activation-observability.ts:323-329`); `activation_settled` maps to waiting (`src/specialist/native-activation-observability.ts:249-250`). For each resumed native active segment of duration `Δ`, `xtrm_job_active_runtime_seconds_sum` is low by `Δ`, and `xtrm_job_wait_seconds_sum` is high by `Δ`. Summed `rate(..._sum)` across a mixed fleet inherits those equal-and-opposite errors, and histogram buckets/quantiles cannot repair them.

### Medium — chain durations use different run-start boundaries

The chain metric uses `max(completed_at_ms) − min(started_at_ms)` (`src/specialist/prometheus-projection.ts:317-329`), where job-metric start is the earliest persisted timeline event (`src/specialist/observability-sqlite.ts:2900-2902`). Legacy persists `run_start` before FIFO/session setup (`src/specialist/supervisor.ts:1515-1543`); native emits `activation_started` only after the session and activation snapshot exist (`src/activation/native-host.ts:1765-1778`), and that signal becomes `run_start` (`src/specialist/native-activation-observability.ts:241-248`). Native request/admission/starting signals are suppressed from the timeline (`src/specialist/native-activation-observability.ts:50-59`). If the desired origin is dispatch time `D_i` and stored start is `S_i=D_i+δ_i`, observed chain duration is `C_max−min(S_i)` rather than `C_max−min(D_i)`; error is `min(D_i)−min(D_i+δ_i)`, normally a negative undercount by the earliest member’s omitted startup/admission lag. A mixed chain can also change which member supplies the minimum.

## 8. Classifier/producer/consumer gaps

### Metric classifiers with no shipped production input

All eight forensic families are classifier-only in production: `xtrm_mcp_operations_total`, `xtrm_gate_verdicts_total`, `xtrm_evidence_refs_total`, `xtrm_identity_operations_total`, `xtrm_policy_decisions_total`, `xtrm_policy_mismatches_total`, `xtrm_eval_score`, and `xtrm_eval_runs_total` (`src/specialist/prometheus-projection.ts:456-600`). The production collector omits `forensicEvents` (`src/specialist/prometheus-projection.ts:84-95`); only direct tests inject them (`tests/unit/specialist/prometheus-projection.test.ts:158-322`).

Within source producers, MCP events do exist (`src/mcp/v2-server.ts:203-229`; `src/server.ts:207-250`), and evidence-bearing auto-commit events exist (`src/specialist/supervisor.ts:1829-1851`; `src/specialist/forensic-events.ts:729-742`). Direct grep found no runtime producer for `identity`, `policy`, or `eval` families, and no runtime producer of review verdict timeline types; this is a verified negative source search, while the classifier/type declarations are at `src/specialist/prometheus-projection.ts:495-585` and `src/specialist/forensic-events.ts:825-866`.

### Producers with no direct Prometheus forensic consumer

The forensic mapper produces `job`, `tool`, `turn`, `model`, `control`, `retry`, `compaction`, `error`, `git`, `command`, `chain`, `worktree`, and `process_health` families (`src/specialist/forensic-events.ts:813-829`), but `samplesForForensicEvent` has direct branches only for MCP, review, evidence, identity, policy, and eval, then returns no samples (`src/specialist/prometheus-projection.ts:479-588`). Some job/tool/turn/model data is independently re-aggregated through `specialist_job_metrics`; that is not consumption of these forensic rows (`src/specialist/observability-sqlite.ts:2873-2988`). `lifecycle` dead-job events are also produced with no direct metric classifier (`src/specialist/dead-job-audit.ts:60-90`).

A narrower same-family loss also exists: both MCP servers produce `mcp.call.started` (`src/mcp/v2-server.ts:203-209`; `src/server.ts:207-208`), but `resultForMcpEvent` does not classify it, so it emits no sample (`src/specialist/prometheus-projection.ts:636-640`).

No alert, recording rule, dashboard, or PromQL consumer of any `xtrm_*` metric exists in `src/`; this is a verified negative direct grep. The only in-tree consumers are the two exporters and tests cited above.
