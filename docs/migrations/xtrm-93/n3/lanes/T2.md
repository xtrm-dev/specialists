## 4. Concurrency and write atomicity

| Mechanism | Finding |
|---|---|
| Journal/lock | Every open initializes/enforces WAL and verifies it; persistent and init connections set `busy_timeout=5000` ms (`src/specialist/observability-sqlite.ts:171-185`, `src/specialist/observability-sqlite.ts:1478-1489`, `src/specialist/observability-sqlite.ts:3405-3414`). Cross-process writers therefore assume SQLite WAL serialization; there is no process-global writer lock. Verdict: **PARITY**. |
| Retry | Intended policy is five attempts, exponential `50ms * 2^attempt + jitter`, capped at 5s, for BUSY/LOCKED/lock-text and any UNIQUE failure (`src/specialist/observability-sqlite.ts:108-163`). **Node path calls `Bun.sleepSync` unconditionally**, although Node is explicitly supported (`src/specialist/observability-sqlite.ts:4-18`, `src/specialist/observability-sqlite.ts:158-160`); the first retryable conflict under Node can fail with `Bun is not defined`. Verdict: **NATIVE_GAP**. |
| Transactions | The Node shim uses `BEGIN`/`COMMIT` and rolls back on throw (`src/specialist/observability-sqlite.ts:67-82`). Status+event(s), terminal status+event+result, node row+event and claim are atomic (`src/specialist/observability-sqlite.ts:1286-1303`, `src/specialist/observability-sqlite.ts:2041-2075`, `src/specialist/observability-sqlite.ts:2196-2223`). Single `appendEvent` is not wrapped in an explicit transaction (`src/specialist/observability-sqlite.ts:2078-2087`). |
| Sequence allocation | Writers use `MAX(seq)+1`; requested seq is accepted only if absent in both timeline and forensic tables, otherwise it is renumbered to the max next seq across both (`src/specialist/observability-sqlite.ts:1582-1607`, `src/specialist/observability-sqlite.ts:1610-1654`). `specialist_forensic_events` alone has `UNIQUE(job_id,seq)`; specialist/node `(owner,seq)` indexes are non-unique (`src/specialist/observability-sqlite.ts:347`, `src/specialist/observability-sqlite.ts:819-822`). A racing transactional writer rolls back and recomputes on retry. A racing standalone `appendEvent` can commit the timeline insert before the forensic UNIQUE failure, then retry with a new seq and leave a duplicate/orphan timeline row. Verdict: **SEMANTIC_DIVERGENCE**. |
| Active claim | Claim lookup/cancel/write/event is transactional and stale claims require age >60s plus dead PID (`src/specialist/observability-sqlite.ts:1257-1303`). The unique active-bead index excludes `waiting` while lookup includes it (`src/specialist/observability-sqlite.ts:944`, `src/specialist/observability-sqlite.ts:1782-1786`): application transaction protects one connection, but the DB invariant does not cover cross-process waiting claims. Verdict: **SEMANTIC_DIVERGENCE**. |

## 5. Retention and `sp db`

`sp db prune` requires `--before`, defaults to dry-run, and only applies with `--apply`; `--include-epics` and `--skip-extract` are opt-ins (`src/cli/db.ts:178-227`, `src/cli/db.ts:503-530`). Event retention is separately fixed at **30 days** (`eventsRetentionMs` default), independent of `--before` (`src/specialist/observability-sqlite.ts:3109-3115`, `src/cli/db.ts:113-116`).

| Table | Delete rule |

## 7. `sp ps` native-activation enumeration

Current code calls `readForensicEvents({jobIdPrefix:'act:', sinceMs, limit:1000, order:'desc'})`, groups those rows into activation summaries, applies bead/mine filters afterward, and displays at most 10 summaries (`src/cli/ps.ts:742-764`, `src/cli/ps.ts:766-776`). `readForensicEvents` clamps and applies `LIMIT` directly to `specialist_forensic_events` after `ORDER BY t,seq,id` (`src/specialist/observability-sqlite.ts:2797-2816`). Therefore **1000 bounds raw event rows, not activation IDs**; one noisy activation can consume the entire window. Verdict: **NATIVE_GAP**.

The key one-row-per-activation relation already exists: **`specialist_jobs`**, keyed by `job_id`, with `updated_at_ms` and identity/status columns; native adapter uses `activationId` as status `id` and upserts that row (`src/specialist/observability-sqlite.ts:553-568`, `src/activation/forensic-sink.ts:96-126`, `src/activation/forensic-sink.ts:165-177`). A bounded two-stage query is therefore constructible now:

```sql
WITH latest AS (
  SELECT job_id
  FROM specialist_jobs
  WHERE job_id >= 'act:' AND job_id < 'act:\uffff'
  ORDER BY updated_at_ms DESC, job_id DESC
  LIMIT :n
)
SELECT e.*
FROM latest a JOIN specialist_forensic_events e ON e.job_id = a.job_id
ORDER BY e.t DESC, e.seq DESC, e.id DESC;
```

The activation prefix range is the same case-sensitive strategy already used by `readForensicEvents`, and the event join is backed by the forensic job indexes (`src/specialist/observability-sqlite.ts:1177-1183`, `src/specialist/observability-sqlite.ts:2801-2815`, `src/specialist/observability-sqlite.ts:347-350`). **However, it is not fully order-index-backed today:** no jobs index starts with `updated_at_ms` while selecting native IDs; the job PK backs the prefix range, then SQLite sorts candidate activations. A schema-only copy of the real DB produced `SEARCH specialist_jobs USING ... (job_id>? AND job_id<?)` plus `USE TEMP B-TREE FOR ORDER BY`, then an indexed event lookup (runtime-plan evidence, explicitly unverified by source). Add a native/latest jobs index (or an engine discriminator plus `(engine,updated_at_ms DESC,job_id DESC)`) to make latest-N selection fully index-ordered. Verdict: **ADAPTER_NEEDED**; **bounded latest-N IDs + indexed event fetch is constructible now, but a fully index-ordered latest-N selector is not**.
