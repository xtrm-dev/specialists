# T5 — Model, fallback, and provider telemetry

Evidence tree: `/home/dawid/dev/specialists/.xtrm/worktrees/specialists-xt-pi-8158-recon` (read-only inspection).

## Finding

Native `model_fallback` is silently dropped. `mapNativeLifecycleEvent` has no `model_fallback` arm and its default returns `null` (`src/specialist/native-activation-observability.ts:236-306`). It is also absent from both declared gap sets (`src/specialist/native-activation-observability.ts:50-89`), so the sink persists only the status update and no timeline/forensic row (`src/activation/forensic-sink.ts:181-245`). The migration audit already identifies this as a major silent-loss blocker (`docs/migrations/xtrm-93/telemetry-delta.md:342-348`).

**Classification now:** `NATIVE_GAP`, not intentional absence. There are **five emit sites with three distinct meanings**. The canonical durable fallback row should be the shared `fallback_step` row, not a native-only `model_fallback` row.

## 2. Which model/provider actually executed, and at what boundary?

The strongest durable execution evidence is the `meta` row generated from the provider's assistant `message_start`: it records the message's actual `model` and `provider` (`src/specialist/native-activation-observability.ts:330-337`). This is an execution boundary, unlike availability resolution or session construction. The durable forensic sink attaches it to the activation/attempt and writes it with the surrounding status transaction (`src/activation/forensic-sink.ts:165-177,279-290`; `src/specialist/observability-sqlite.ts:1631-1653`).

At terminal settlement, native `run_complete` records the snapshot's current `resolvedModel` and derives backend/provider from its prefix (`src/specialist/native-activation-observability.ts:251-270`). Legacy records callback metadata when the session reports model/backend (`src/specialist/supervisor.ts:2413-2418`) and writes the final model/backend at completion (`src/specialist/supervisor.ts:2754-2765,2777-2790`).

Limit: if a provider attempt fails before assistant `message_start`, there is no provider-confirmed execution row. The attempted candidate then exists only in fallback/error evidence; native fallback evidence is currently dropped. Therefore “session selected/resolved” and “provider actually produced a turn” must remain separate facts.

## 3. Every native `model_fallback` emit and its meaning

There are **five emit sites** and **three semantic meanings**:

| Site | Trigger | Payload | Meaning |
|---|---|---|---|
| `src/activation/native-host.ts:1199-1207` | Admission-time candidate fails model availability validation and another configured candidate exists. | `from_model`, `to_model`, `error_class:'unavailable'`, `note`, `terminal:false` | **M1 — dispatch-time candidate skip.** No session or provider execution has occurred. |
| `src/activation/native-host.ts:2220-2234` | A failed provider turn is retryable, but the next chain candidate is unavailable. | `from_model`, `to_model`, `error_class:'unavailable'`, `note`, `terminal:true` | **M3 — terminal degradation/no switch.** |
| `src/activation/native-host.ts:2236-2244` | A failed provider turn is retryable and the next candidate passed availability validation. | `from_model`, `to_model`, classified `error_class`, `terminal:false` | **M2 — runtime switch is proposed.** It is emitted before lease acquisition and session creation, so it is not proof that the fallback model executed. |
| `src/activation/native-host.ts:2274-2285` | Write-lease acquisition for the replacement session fails. | `from_model`, `to_model`, `error_class:'unavailable'`, `note`, `terminal:true` | **M3 — terminal degradation/no switch.** The original session remains live (`src/activation/native-host.ts:2258-2266`). |
| `src/activation/native-host.ts:2294-2308` | Replacement session construction fails. | `from_model`, `to_model`, `error_class:'unavailable'`, `note`, `terminal:true` | **M3 — terminal degradation/no switch.** |

The actual switch happens only after replacement-session creation: the host disposes the old session, assigns the new session, updates `resolvedModel`, subscribes it, and then runs it (`src/activation/native-host.ts:2312-2324`). Consequently, `terminal:false` means “advance attempted,” not “fallback model executed.”

Preset resolution is a separate stderr JSON event, `preset_resolved` (`src/specialist/loader.ts:676-690`); it is not one of the three `model_fallback` meanings. A preset-resolved model can subsequently participate in M1/M2/M3 because preset references are resolved before the model chain is used (`src/specialist/loader.ts:341-348,427-440`).

## 4. Why fallback happened

Native runtime fallback advances only for `rate_limit`, `timeout`, or `transient` errors (`src/activation/native-host.ts:665-671,2197-2204`). Those classifications come from the shared classifier, which can return `auth`, `rate_limit`, `timeout`, `transient`, or `unknown` (`src/specialist/runner.ts:980-987`). Admission/gate and degradation paths collapse their reason code to `unavailable` and optionally preserve a free-text `note` (`src/activation/native-host.ts:1199-1207,2220-2234,2274-2285,2294-2308`).

What is preserved at source:
- stable broad class: `error_class`;
- free-text availability/lease/session detail on M1/M3: `note`;
- whether another candidate can be attempted: `terminal`;
- source and destination candidates: `from_model`/`to_model`.

What is lost even before the sink: the M2 successful-switch proposal does not include the original error text or provider error/status code (`src/activation/native-host.ts:2236-2244`). What is lost after the sink: all of the above, because the mapper returns no row (`src/specialist/native-activation-observability.ts:236-306,625-635`). Exact provider reason-code preservation is therefore **unsupported/unverified** beyond the broad classifier and optional free-text note.

## 5. Attempt identity

Attempt identity **is available in the native event envelope**, but not in any `model_fallback` payload. The host's sink envelope and emit closure carry `activationId` and `attemptId` (`src/activation/native-host.ts:680-689,875-890`), and the forensic sink carries that attempt identity into its projection (`src/activation/forensic-sink.ts:92-94,181-190`). A mapped row would be written with `activation_id` and `attempt_id` by the SQLite writer (`src/specialist/observability-sqlite.ts:1631-1653`).

Runtime model-chain fallback intentionally remains within the same activation and attempt (`src/activation/native-host.ts:2185-2195`). Explicit retry is different: it advances `attemptId` (`src/activation/native-host.ts:2331-2337,2383-2405`).

Today there is no durable native fallback row, so there is no queryable fallback-to-attempt link. After mapping, use the outer SQLite `attempt_id`; do **not** overload legacy `attempt_n`. Legacy `attempt_n` is the model-chain ordinal emitted as `modelIndex + 2` (`src/specialist/runner.ts:1356-1363,1398-1405`), not activation-attempt identity.

## 6. Usage attribution per model/provider

**No direct, reliable per-model attribution exists today.** Native converts each `message_end` usage into `token_usage`, but the row contains token counts only, with no model/provider/session key (`src/specialist/native-activation-observability.ts:339-351,473-484`). The host accumulates those counts across the activation (`src/activation/native-host.ts:1913-1924`), including fallback sessions. SQLite metrics then retain one final `model` plus aggregate token trajectories (`src/specialist/observability-sqlite.ts:2873-2884,2940-2946`).

Prometheus labels the aggregate with the job's final model and derives provider from that model's prefix (`src/specialist/prometheus-projection.ts:369-375,410-422`). Thus, when primary and fallback models both consume tokens, their combined usage is attributed to one final model/provider. Adjacency to a preceding `meta` row could be guessed, but that is inference rather than a row-level join and fails for pre-`message_start` failures or interleaving.

Required fix: every usage delta/cumulative row must carry the execution model, provider, and session/model-leg identity at emission. The activation/attempt keys alone are insufficient because fallback intentionally stays within one attempt (`src/activation/native-host.ts:2185-2195`). Existing Prometheus cardinality policy must remain unchanged: normalized names longer than 80 characters become `other`, and provider comes from the model prefix (`src/specialist/prometheus-projection.ts:819-829`).

## 7. Canonical representation that answers all six questions without inference

Use these explicit durable facts:

1. **Selection intent row at admission:** persist configured model, requested model, resolved model, override boolean, ordered resolved chain, and activation/attempt identity. The current `activation_admitted` source payload already has the first four fields (`src/activation/native-host.ts:1534-1545`); the adapter must project it to a shared row instead of status-only suppression (`src/specialist/native-activation-observability.ts:50-54,236-306`).
2. **One shared `fallback_step` row per M1/M2/M3 decision:** include outer `activation_id`/`attempt_id`; preserve `from_model`, `to_model`, `error_class`, `note`, `terminal`; add a stable `outcome` (`candidate_skipped`, `switch_proposed`, `candidate_unavailable`, `lease_denied`, `session_create_failed`). Do not claim execution from `switch_proposed`.
3. **Execution-boundary `meta` row:** retain provider-reported model/provider/session on assistant `message_start` (`src/specialist/native-activation-observability.ts:330-337`). This is the proof of which candidate executed.
4. **Usage row:** include that same model/provider/session/model-leg directly on each token row; do not infer it from timeline order.
5. **Terminal row:** retain final resolved model/provider and `fallback_used`; the current in-memory result already has the model-selection fields (`src/activation/types.ts:155-167`), while `run_complete` currently carries final model/provider only (`src/specialist/native-activation-observability.ts:251-270`).

This representation answers initial intent, override, each fallback cause, attempt identity, actual executor, per-model usage, and final winner by direct keys.

## 8. Durable-row ruling and byte compatibility

**Ruling: persist it. Map native `model_fallback` to the shared canonical `fallback_step` event type. Do not create a durable `model_fallback` type.**

Why `fallback_step`:
- legacy already emits the contract `{event:'fallback_step', specialist, attempt_n, model_tried, error_class, terminal}` (`src/specialist/runner.ts:990-1008`);
- operator documentation defines that same event and field vocabulary (`docs/overrides-guide.md:285`);
- CLI tests pin chronological, flat `fallback_step` rows and their field names/literals (`tests/unit/cli/log.test.ts:126-162`);
- the live fallback test expects `fallback_step` rows in operator logs (`tests/integration/cli/run-fallback-chain.live.test.ts:146-151`).

Byte-compatibility requirements:
- Keep existing legacy-produced `fallback_step` JSON unchanged: same `event`, `specialist`, `attempt_n`, `model_tried`, `error_class`, and `terminal` keys, value types, and units (`src/specialist/runner.ts:990-1008`).
- Preserve the existing flat timeline representation pinned by `tests/unit/cli/log.test.ts:126-162`; do not nest the existing keys or rename `attempt_n`.
- Treat `attempt_n` as the legacy model-chain ordinal, never as activation attempt identity (`src/specialist/runner.ts:1356-1363,1398-1405`). Carry native attempt identity in the existing outer SQLite `attempt_id` (`src/specialist/observability-sqlite.ts:1631-1653`).
- Add native-only detail only as additive fields on new native-produced rows (`from_model`, `to_model`, `note`, `outcome`); do not change bytes emitted by the legacy producer. Existing `model_change`, `run_complete`, and Prometheus metric/label names remain unchanged.
- Because the current M2 event precedes actual switch installation (`src/activation/native-host.ts:2236-2244,2312-2324`), its canonical outcome must remain `switch_proposed`; the later provider `meta` row is execution proof.

The legacy callback also lacks a mapper case: its `fallback_step` event reaches `mapSessionEventToTimeline`, whose default returns `null` (`src/specialist/timeline-events.ts:541-768`). Therefore parity requires one shared adapter used by both native and legacy producers, not only adding `model_fallback` to the native switch.
