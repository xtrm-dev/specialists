## Exact double-count arithmetic

1. Every boundary carrying U is persisted as both `token_usage(U)` and `turn_summary(...,U)` on legacy (`src/specialist/supervisor.ts:2329-2333,2353-2373`) and native (`src/specialist/native-activation-observability.ts:342-352`); aggregation appends both (`src/specialist/observability-sqlite.ts:2909-2918`). Naïve trajectory sum for boundaries `U1…Un` is `Σ(Ui+Ui)=2ΣUi`; with `U1=100,U2=150`, it reports 500 instead of 250.
2. For session-cumulative reports `C1=100,C2=250,C3=400`, spend is `C3=400`; naïve sum is `100+250+400=750`, double-counting prefixes by 350. The accumulator tries to difference such observations (`src/specialist/native-activation-observability.ts:162-195`), but the raw trajectory does not tag the form (`src/specialist/observability-sqlite.ts:2909-2918`).
3. Legacy can derive `T=I+O+CW+CR` (`src/pi/session.ts:723-732`). Naïvely adding the total and those components yields `T+I+O+CW+CR=2T`; because each event is duplicated in trajectory, summing all fields of both rows yields `4T` for that one boundary. Reasoning/tool are not in that legacy fallback formula (`src/pi/session.ts:723-732`) and must not be assumed included or excluded from a provider total.

## `accumulateTokenUsage`: soundness and admitted failure modes

**Not sound as a general shape detector / ADAPTER_NEEDED.** Its own contract admits that providers use both delta and cumulative messages and that an all-growing delta sequence is misclassified and undercounted (`src/specialist/native-activation-observability.ts:162-175`). The implementation decides one mode for the whole message from `every(carried key is absent-or-nondecreasing)`, ignores zero/absent keys, then either adds each whole value or its difference (`:183-195`). The forms are value-indistinguishable: delta messages 100,200,300 become `100+(200−100)+(300−200)=300`, although true spend is 600. Classification can **flap** whenever one carried counter decreases; stored totals do not flap because only positive values/nonnegative differences are added (`:183-195`). The doc's “never … explodes” ceiling (`:173-175`) does not hold for real mixed/reset shapes: after `{input:100,output:50}`, `{input:200,output:20}` makes the whole second message “delta”, producing input 300 although a cumulative input counter says 200. A cumulative input plus per-message/reset output/cache counter, a per-key provider reset, or a new session whose first values all exceed the prior session's last values can respectively overcount, repeatedly re-add a cumulative prefix, or undercount by subtracting the prior session. This risk crosses resume/retry because `lastUsageSeen` is keyed by the activation snapshot and intentionally survives attempts (`src/activation/native-host.ts:832-838`); forensic state likewise survives by `activationId` (`src/activation/forensic-sink.ts:163-185,253-277`).

## Direct answers

1. **Naïve-sum double counts:** exact arithmetic is above: duplicate event pair `2ΣUi`; cumulative-prefix sum `ΣCi` instead of `Cn`; total-plus-components `2T`, or `4T` when combined with duplicate rows.
2. **Heuristic:** no; it can switch classification, remains output-monotonic, undercounts all-growing deltas/new-session resets, and can overcount/explode mixed per-key or partially reset cumulative shapes (`src/specialist/native-activation-observability.ts:162-195`; `src/activation/native-host.ts:832-838`).
3. **Turns:** native `run_complete.metrics.turns` is activation-cumulative `turn_start` count (`src/activation/forensic-sink.ts:264-270`; `src/specialist/native-activation-observability.ts:252-269`). `total_turns` is assistant `message_end`/`turn_summary` row count (`src/specialist/native-activation-observability.ts:342-353`; `src/specialist/observability-sqlite.ts:2909-2913`). **Not the same counter.** Native host Fleet `turn_count` is yet another, based on `turn_end` (`src/activation/native-host.ts:1950-1957,2614-2624`).
4. **Native context:** no native producer populates `context_pct`. It is omitted at native `createTurnSummaryEvent` (`src/specialist/native-activation-observability.ts:342-352`) and from native status (`src/activation/forensic-sink.ts:103-126`), so aggregation skips it (`src/specialist/observability-sqlite.ts:2909-2913`), member query returns null (`:2363-2379`), live aggregation filters it out (`src/specialist/live-aggregates.ts:148-160`), and Prom emits no gauge (`src/specialist/prometheus-projection.ts:685-696`). **Rule: absence means not observed and must remain absent; zero is only valid when measured.**
5. **Additive-only change:** do not rename or reinterpret any existing value. Add `basis_v1` beside every trajectory observation (`boundary`, `granularity`, `scope`, actual `activation_id`/`attempt_id`/`pi_session_id`, `counter_form:"provider_reported"`, `total_origin`) and add separately named `session_cumulative`, `attempt_cumulative`, and `activation_cumulative` objects with an `algorithm` tag. Add `turn_counts` and `compactions` split by boundary/phase, and unit-tagged context observations. Update readers to unwrap existing `token_usage` while accepting old flat fixtures; aggregate native completion through the same existing aggregator; keep existing `total_turns`, `metrics.turns`, token values, and absent native context unchanged (`src/specialist/observability-sqlite.ts:2852-3029`; `src/activation/forensic-sink.ts:219-245`).
