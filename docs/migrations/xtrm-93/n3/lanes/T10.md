# T10 — extension / admission telemetry

Base inspected: `feature/xtrm-93-n0n2-recon` at `553b5a23` (verified from the requested worktree). This report is static-source evidence only; no repository files or tests were changed or run.

## Verdict

The enforcement path is functionally closed, but its telemetry is not. The host emits extension-specific lifecycle signals, yet `mapNativeLifecycleEvent()` returns `null` for every extension signal because only run lifecycle, lease/tool control, and terminal rejection names are mapped; `createActivationForensicSink()` then performs only a `specialist_jobs` status upsert when the mapped event is null. Therefore `extension_discovery_sessions`, pinned/refused tools, finalized admission tools, and fallback mismatch detail do not produce `specialist_events` or `specialist_forensic_events` rows today (`src/specialist/native-activation-observability.ts:235-305`; `src/activation/forensic-sink.ts:206-245`).

N3 must keep discover-then-pin unchanged. The minimum migration is to project extension/admission decisions onto the existing `control_signal` timeline type, following the existing lease-admission precedent, rather than introduce a parallel native event vocabulary (`src/specialist/native-activation-observability.ts:271-290`). Discovery/baseline sessions must remain non-job, non-turn, zero-usage observations.

## 4. Dynamic activation double `session_start`

**Bound:** a dynamic activation creates one source-free baseline session and one source-loaded discovery session, each disposed in `finally`; no dynamic sources returns before either is created (`src/activation/native-host.ts:402-435,449-452,487-518,592-595`). The real model session is a third session created later (`src/activation/native-host.ts:1660-1704`). Thus an enabled dynamic extension runs its load-time/session-start work in discovery and again in the real session, while the baseline session deliberately has no dynamic extension paths (`src/activation/native-host.ts:408-418,499-517,1606-1611`).

**Observation:** the host emits `extension_discovery_sessions{fenced_sessions:2,...}` on success and failure (`src/activation/native-host.ts:1263-1301`), and the unit oracle proves exactly baseline + discovery + real and disposal (`tests/unit/specialist/activation-native-host.test.ts:3804-3835`). The canonical telemetry adapter drops that observation and represents only the real session as `run_start`/`pi_session_id` (`src/specialist/native-activation-observability.ts:242-248,304-305`). Therefore telemetry currently represents **one of three sessions**, not both fenced sessions; it also does not durably represent the count.

## 5. Reserved-name refusal layers

`ask_coordinator` and `escalate_to_coordinator` are stable host custom-tool names (`src/activation/ask-tool.ts:52-54`). They are independently unpinnable at these layers:

1. **Required reserved-set shadow refusal.** The call site includes base native tools, base extension tools, and both host tools in required `reservedNames`; discovery throws when any reserved name has non-builtin provenance (`src/activation/native-host.ts:1286-1297,555-563`). This layer emits `activation_rejected(reason=extension_tool_shadowed)` through the common rejection path (`src/activation/native-host.ts:1298-1307,957-967`). Canonical telemetry persists only generic terminal error, not tool/source detail (`src/specialist/native-activation-observability.ts:291-303`).
2. **Explicit discovery pin filter.** Even when the registry lacks enough provenance for the shadow throw, either host name is put in `refusedProvenance` and never in `pinned` (`src/activation/native-host.ts:567-574`). The host emits `extension_tools_refused` when this layer fires (`src/activation/native-host.ts:1314-1319`), but the adapter drops it (`src/specialist/native-activation-observability.ts:304-305`).
3. **Effective-contract defense in depth.** `withDiscoveredExtensionTools()` filters both literals from `safePinned` even if upstream passes them (`src/specialist/resolved-tool-contract.ts:169-180`). This layer emits no telemetry. Its executable oracle is `tests/unit/specialist/resolved-tool-contract.test.ts:159-167`.

The shadow-refusal integration oracle proves `ask_coordinator` refusal, disposal of both fenced sessions, no real session, and no lease (`tests/unit/specialist/activation-native-host.test.ts:3663-3686`). There is no equivalent integration case for `escalate_to_coordinator`; coverage is only the shared code path plus pure materialization test, so a dedicated symmetric test is recommended.
