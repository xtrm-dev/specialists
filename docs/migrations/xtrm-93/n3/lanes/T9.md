## Executive verdict

- **10 unique settlement names at 19 `emit(...)` sites; 0/10 become durable timeline or forensic events.** Every name falls through `mapNativeLifecycleEvent` to `null`; the sink then performs only a generic status upsert, with neither the name nor payload (`src/specialist/native-activation-observability.ts:235-305`; `src/activation/forensic-sink.ts:206-245`; `src/specialist/observability-sqlite.ts:2007-2011`).
- The underlying settlement can still persist in the file store, `work_receipts`, `artifact_bindings`, and `issue_journal`; this is operational state, not durable evidence that a particular telemetry signal fired (`src/activation/settlement-store.ts:166-208`; `substrate:src/store/migrations/006_provenance.ts:28-54`; `substrate:src/store/migrations/005_journal.ts:9-26`).
- **Exactly-once is conditional, not end-to-end.** Same-machine publishers of one `(activation, attempt)` are serialized by an atomic hard-link lease, and crash recovery reconciles producer rows before writing (`src/activation/workspace-lease.ts:277-326`; `src/activation/settlement-publication.ts:280-345,411-420`). There is no receipt uniqueness constraint on `execution_binding_id`, no Journal uniqueness key on `(activation,attempt)`, and the lease explicitly does not serialize different machines (`substrate:src/store/migrations/006_provenance.ts:28-41`; `substrate:src/store/migrations/005_journal.ts:9-26`; `src/activation/settlement-lease.ts:44-53`).
- **`activation_settled` does not mean published.** It is emitted before validation, before the `ActivationResult` is constructed, and before settlement storage/publication (`src/activation/native-host.ts:2034-2084`). It maps only to a waiting status change (`src/specialist/native-activation-observability.ts:249-250`).
- Settlement retention is unbounded: one JSON file per terminal `(activation,attempt)`, including failed attempts and unbounded raw output; the store exposes no delete/compact operation (`src/activation/settlement-store.ts:50-68,91-112,166-208`; `src/activation/settlement-publication.ts:87-95`).

### Settlement-file write atomicity: proved from the sequence

`save` computes the final path, creates the activation directory, and calls `writeFileSync(finalPath, JSON.stringify(record), 'utf8')` directly (`src/activation/settlement-store.ts:168-176`). The module imports `writeFileSync` but no `renameSync`, `linkSync`, `openSync`, or `fsyncSync`; the save sequence has no staging path, temp write, file fsync, atomic rename/link, directory fsync, append flag, lock, or compare-and-swap (`src/activation/settlement-store.ts:14,166-177`). This is a plain replacement of the sole final-path file, not write-then-rename or temp+fsync+rename.

The open crash window is the direct overwrite itself: if the process dies after replacement starts but before the full unbounded JSON is written/durable, the final path can contain empty/partial JSON rather than the prior complete record. `get` catches parse/read failure and returns `undefined`; `listAttempts` and backlog scans silently skip that file (`src/activation/settlement-store.ts:178-199,210-243`). The closed window is only filename multiplicity: one `(activation,attempt)` maps to one path, so a normal completed save replaces rather than creates a second settlement file (`src/activation/settlement-store.ts:168-176`). It does **not** close torn-write, lost-update, or durability-before-power-loss windows.

### 2.2 Conditional exactly-once verdict

**Verdict: `SEMANTIC_DIVERGENCE` from an unconditional “exactly once” claim.** The implemented guarantee is: at most one same-machine publisher is admitted for one `(activation,attempt)`, and a later republisher reuses a receipt and Journal entry discoverable through the current producer (`src/activation/settlement-lease.ts:11-26,117-165`; `src/activation/settlement-publication.ts:280-420`). The producer itself does not enforce receipt or result uniqueness by settlement identity (`substrate:src/store/migrations/006_provenance.ts:28-41`; `substrate:src/store/migrations/005_journal.ts:9-26`).

Duplicate/loss boundaries:

1. **Cross-machine duplicate is possible:** the lease is per-machine, while two hosts can share one Substrate store (`src/activation/settlement-lease.ts:44-53`).
2. **Direct `publishSettlement` replay after the first call completes can duplicate:** it overwrites the local record before taking the lock and allocates without producer reconciliation (`src/activation/settlement-publication.ts:547-605,673-682`). Reconciliation protects `republishSettlement`, not the initial function (`src/activation/settlement-publication.ts:280-345`).
3. **Pre-store and torn-store loss are possible:** publication returns immediately on save error, and torn files are skipped (`src/activation/settlement-publication.ts:560-567`; `src/activation/settlement-store.ts:193-198,236-240`).
4. **Unverifiable dead-holder loss/wedge is possible:** without verifiable `/proc` liveness, a crashed lease is never reclaimed (`src/activation/settlement-lease.ts:44-53`).
5. **Receipt/Journal crash windows are recoverable when reads are available:** producer rows are reconciled under the exclusion and reused (`src/activation/settlement-publication.ts:292-345,347-405`).
6. **Automatic revival bug:** `republishOncePerProcess` returns when `listPendingPublication()` is empty, before `republishPendingSettlements` can add `listRuntimeRefused()` records. A store containing only `runtime_lacks_settlement_surface` refusals is therefore not automatically revived after upgrade (`src/activation/native-host.ts:1863-1870`; `src/activation/settlement-publication.ts:450-460`). The unit test calls `republishPendingSettlements` directly and does not cover this host gate (`tests/unit/specialist/settlement-exclusion.test.ts:319-341`).

### 2.3 Provenance, revision, and closure

- `WorkReceipt` contains `executionBindingId`, `issueId`, `issueRevision`, and `contractHash` (`substrate:src/domain/provenance.ts:22-33`). Allocation copies these fields from the binding, not from model output (`substrate:src/service/provenance-service.ts:244-278`).
- The execution binding atomically pins the dispatch-time live revision/hash and rejects a stale expected pin (`substrate:src/service/provenance-service.ts:118-158,211-230`).
- The Journal result does **not** reuse that pinned revision column: `appendEntry` reads `issue.currentRevision` at publication time (`substrate:src/service/journal-service.ts:217-251`). If the issue changes after dispatch, the receipt remains on the bound revision while `issue_journal.issue_revision` records the later revision; the result payload’s `provenanceRefs` is the route back to binding/receipt (`src/activation/settlement-publication.ts:621-639`). Treating the Journal row’s revision as “revision executed” is therefore a **SEMANTIC_DIVERGENCE** (`substrate:src/service/journal-service.ts:217-251`; `substrate:src/service/provenance-service.ts:244-278`).
- Settlement does not close the issue. `SpecialistWorkItemBoundary` has settlement append/receipt/artifact methods but no closure method (`src/activation/workitem-store.ts:370-415`). Closure is a separate transaction requiring reason, actor, and explicit result/receipt/artifact refs; it writes `issue_closures`, changes lifecycle state, and appends closure events (`substrate:src/service/closure-service.ts:146-204`). Thus **settled ≠ published ≠ closed**.

## 4. The rule: settled ≠ published

**No. `activation_settled` is not equivalent to a published result.**

1. The host emits `activation_settled` immediately after idle/stop-reason checks (`src/activation/native-host.ts:2034-2039`).
2. Validation occurs afterwards and can fail while the activation still produces a `completed` result (`src/activation/native-host.ts:2041-2071`).
3. `activation_completed` and the durable observability result write occur before `publishTerminalSettlement` (`src/activation/native-host.ts:2056-2084`; `src/activation/forensic-sink.ts:219-245`).
4. Settlement storage can fail and publication can degrade/refuse while the activation result remains completed (`src/activation/settlement-publication.ts:502-513,560-583,656-680`; `src/activation/native-host.ts:2137-2182`).
5. `activation_settled` maps only to `status_change(waiting)` and contains no receipt, Journal, or publication state (`src/specialist/native-activation-observability.ts:249-250`).

Therefore an operator must require the settlement record’s links or producer rows, never `activation_settled`, `activation_completed`, or `specialist_results` alone, to assert publication (`src/activation/settlement-store.ts:158-163`).

## 5. Retention and growth

**Confirmed unbounded.** Production defaults to `.specialists/settlements` under the host cwd (`src/activation/native-host.ts:852-865`). The file store writes one JSON file per `(activationId,attemptId)`, stores failed attempts, and provides only `save/get/listAttempts/listPendingPublication/listRuntimeRefused` (`src/activation/settlement-store.ts:50-112,166-208`). No deletion primitive is imported or exposed (`src/activation/settlement-store.ts:14,91-112`). Raw output is deliberately untruncated in this store (`src/activation/settlement-publication.ts:87-95`; `src/activation/settlement-store.ts:61-62`).

Growth is **O(total terminal attempts)** files and **O(sum of raw result bytes + JSON metadata)** bytes; retry/resume advances attempt identity and therefore adds another file (`src/activation/native-host.ts:2348-2405,2710-2747`; `src/activation/settlement-store.ts:168-176`). A failed attempt also adds a file but no receipt or Journal result (`src/activation/settlement-publication.ts:570-572`).

## 6. Canonical shared representation

### Recommendation

Use the existing shared `control_signal` timeline type for all 10 names, with `action` equal to the exact current emit name, `source:'runtime'`, and the original payload preserved under `metadata`. This is the minimum additive adapter: `control_signal` is already a shared legacy/native type and is already used to make native-only lease/admission facts durable (`src/specialist/timeline-events.ts:414-430,947-956`; `src/specialist/native-activation-observability.ts:271-290`). It avoids inventing a native-only `settlement_*` timeline type and avoids incorrectly reusing `run_complete`, which already means result production rather than publication (`src/specialist/timeline-events.ts:236-301`).

### Per-name disposition — no undecided signals

Every name is **MAP**; none is retired or merged. Merging would destroy distinctions that the file state already tries to preserve, while retiring would leave a producer-side failure/recovery decision observable only through conflated state or stderr (`src/activation/settlement-store.ts:69-83`; `src/activation/native-host.ts:1885-1896`).

| emit name | decision | shared canonical type and meaning | byte-compatibility requirement |
|---|---|---|---|

| `settlement_stored` | **MAP** | `control_signal`, action `settlement_stored`: runtime-store write committed | Same shared-type bytes; preserve `{ref,status}` exactly (`src/activation/settlement-publication.ts:568`; `src/specialist/timeline-events.ts:414-430`). |

Required adapter payload for **every** action: `{source:'runtime', metadata:{...originalPayload, issue_ref, activation_id, attempt_id}}`. The added identity is mandatory because republish emits under a synthetic activation and several republish sub-signals omit the original activation/attempt from their payload (`src/activation/native-host.ts:1876-1883`; `src/activation/settlement-publication.ts:352-406`). Initial events can copy identity from the host envelope (`src/activation/native-host.ts:887-891`).

### Compatibility requirements

- **BYTE_COMPATIBLE_REQUIRED:** keep `schema_version='xtrm.forensic.v1'`, existing forensic envelope/correlation key names, `type:'control_signal'`, `action` exactly equal to the 10 emit names, `source:'runtime'`, and the existing payload key spellings/types (`src/specialist/forensic-events.ts:1,563-608`; `src/specialist/timeline-events.ts:414-430,947-956`).
- Preserve original payload keys (`ref`, `status`, `note`, `receipt`, `kind`, `entry`, `republish`, `partial_receipt`, `contended`, `activationId`, `attemptId`) during the migration; normalized identity keys are additive. There are no pre-existing durable settlement event bytes to migrate because all 10 currently return null (`src/specialist/native-activation-observability.ts:304-305`).
- Existing `control_signal` events must remain unchanged. The forensic classifier currently assigns all control signals `warn`; successful settlement actions need `info`, degraded/deferred/refused need `warn`, and store/republish errors need `error`, without changing legacy control severity (`src/specialist/forensic-events.ts:886-893`).
- `control_signal` maps to forensic family `control` and event name `control.<action>.recorded`; these literals become the shared query vocabulary and require byte-pinned tests (`src/specialist/forensic-events.ts:813-850`).

## 8. What tests actually pin

- The required publication suite drives a live host and pins automatic store → receipt → artifact → Journal behavior and lineage (`tests/unit/specialist/activation-settlement-publication.test.ts:272-352`), failed-attempt/no-publication plus retry identity (`tests/unit/specialist/activation-settlement-publication.test.ts:355-392`), bounded Journal output (`tests/unit/specialist/activation-settlement-publication.test.ts:395-417`), degradation not changing `ActivationResult` (`tests/unit/specialist/activation-settlement-publication.test.ts:420-463`), zero-commit publication (`tests/unit/specialist/activation-settlement-publication.test.ts:465-482`), and reconciliation-based republish outcomes (`tests/unit/specialist/activation-settlement-publication.test.ts:539-765`).
- It does **not** pin durable settlement telemetry. Its sink only collects event names in memory, and the success assertion checks four strings (`tests/unit/specialist/activation-settlement-publication.test.ts:232-235,343-351`). It never uses `createActivationForensicSink` or queries event tables.
- The cross-process suite pins exclusion through deterministic re-entrant calls, explicitly without forking (`tests/unit/specialist/settlement-exclusion.test.ts:19-39,165-300`). It separately pins dead-holder reclaim and reclaim-mutex exclusion (`tests/unit/specialist/settlement-exclusion.test.ts:387-456`). It does not prove multi-machine exclusion, which the implementation explicitly disclaims (`src/activation/settlement-lease.ts:51-53`).
- The shared-observability test checks selected null aliases and the declared gap list, but settlement names are absent from both assertions (`tests/unit/specialist/native-activation-observability.test.ts:290-324`). Therefore adding another dropped settlement name would not fail that oracle.

## Final classification

- Durable settlement telemetry: **`NATIVE_GAP`** for all 10 names (`src/specialist/native-activation-observability.ts:304-305`).
- Migration shape: **`ADAPTER_NEEDED`** — map all names to the shared `control_signal` vocabulary, preserve bytes listed above, and add original identity axes (`src/specialist/timeline-events.ts:414-430,947-956`).
- Exactly-once claim: **`SEMANTIC_DIVERGENCE`** unless scoped to one machine, one initial invocation, a readable file record, and available producer reconciliation (`src/activation/settlement-lease.ts:44-53`; `src/activation/settlement-publication.ts:280-420`).
- Settlement vs closure and retention differences are **`INTENTIONAL_DIFFERENCE`** only if the migration explicitly accepts them; current code proves the behavior but contains no retention policy or automatic closure (`src/activation/settlement-store.ts:91-112,166-208`; `src/activation/workitem-store.ts:370-415`; `substrate:src/service/closure-service.ts:146-204`).
