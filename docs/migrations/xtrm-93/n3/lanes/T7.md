## 1. `sp ps` native enumeration verdict

Current query is exactly `readForensicEvents({ jobIdPrefix:'act:', sinceMs:args.sinceMs, limit:1000, order:'desc' })`; bead/mine filtering occurs **after** summarization (`src/cli/ps.ts:742-756`). The reader translates the prefix to `job_id >= ? AND job_id < ?`, orders globally by `t DESC,seq DESC,id DESC`, and applies `LIMIT ?` (`src/specialist/observability-sqlite.ts:2797-2817`). Therefore **1000 bounds raw forensic event rows, not activation ids**. One activation with the newest 1000 rows yields one summary, hides every quieter activation, caps its displayed `window_event_count` at 1000, and makes `first_event_at_ms` only the first row in that truncated window (`src/specialist/native-activation-summary.ts:160-208`). `--bead` does not prevent starvation because it is applied after the global row window (`src/cli/ps.ts:746-755`). Status: **ADAPTER_NEEDED**.

`specialist_jobs(job_id TEXT PRIMARY KEY,status_json,updated_at_ms,...)` holds one row per current activation; `specialist_job_metrics(job_id PRIMARY KEY,...)` and `specialist_results(job_id PRIMARY KEY,...)` are also one-row-per-job tables but metrics are not populated automatically for native completions (`src/specialist/observability-sqlite.ts:494-519,296-322`). Retired `event_family='activation'` rows can be forensic-only by design, because that vocabulary is explicitly historical (`src/specialist/native-activation-summary.ts:1-10`).

I verified `EXPLAIN QUERY PLAN` against a read-only relevant-table copy of `/home/dawid/dev/specialists/.specialists/db/observability.db` under `/tmp/x93n3`, then deleted the copy. The current query used `idx_forensic_events_job_seq` for the prefix search but a temp B-tree for global time order; a two-stage query (`latest 10 specialist_jobs by updated_at_ms`, then event join) used the `specialist_jobs` PK for prefix selection and `idx_forensic_events_job_seq` for per-id event lookup, with temp B-trees for ordering. Those indexes are defined at `src/specialist/observability-sqlite.ts:227-229,347-350,494-499`. Verdict: **“latest N ids, then their events” is constructible and the event join is index-backed, but the current schema has no `(updated_at_ms,job_id)` index that also satisfies prefix + newest order; selection sorts only the bounded one-row-per-activation candidates.** A fully order-indexed form needs an appropriate new index or a separate activation table/index.

## 2. Window counts presented as totals

The rename landed in both requested renderers: `ps` human and JSON consume `window_event_count/window_turns` (`src/cli/ps.ts:766-776,1115-1158`), and native `feed` human summary prints “turns/events in window” from those names (`src/cli/feed.ts:513-521`). The helper no longer exposes `event_count` or `turns`, and the test asserts both old keys are absent (`tests/unit/cli/native-activation-summary.test.ts:237-256`). **No remaining unlabelled window count was found.** `sp status job.event_count` is a lifetime count because it reads every timeline row, and `db total_turns` is aggregated over the full per-job timeline (`src/cli/status.ts:109-131,317-327`; `src/specialist/observability-sqlite.ts:2852-2988`).

Breaking surface: parsers of `sp ps --json` native rows that require `native_activations[].event_count` or `.turns` now receive missing keys; they must consume `.window_event_count` and `.window_turns` (`src/cli/ps.ts:1157-1158`; `tests/unit/cli/native-activation-summary.test.ts:250-255`). `sp feed`'s native summary is human text, while its native JSON fallback emits raw forensic DB records and never carried either summary count (`src/cli/feed.ts:506-521`).

## 3. Structured field-name compatibility

* Shared rows keep the same identity key across origins: `ps flat[].id`, `status jobs[].id`/`job.id`, `result job.id`, console `ConsoleJob.id`; a native row puts `act:<core>` in that same field because native projection writes `SupervisorStatus.id=activationId` (`src/activation/forensic-sink.ts:96-126`). There is no legacy/native key rename within those shared envelopes.
* `ps` additionally exposes the same native execution in a separate shape using `native_activations[].activation_id` and `state`, not `id` and `status`; this is the only deliberate origin-specific row-key difference in one query (`src/cli/ps.ts:1123-1158`; `src/specialist/native-activation-summary.ts:13-31`).
* `feed --json` is origin-neutral while shared timeline exists, because both are projected through the same pi projector (`src/cli/feed.ts:550-558`; `src/cli/pi-json-output.ts:36-214`). Its forensic-only fallback is intentionally a different DB-record envelope (`src/cli/feed.ts:489-510`).
* `log` default and `forensic` are canonical-origin-neutral. `log --legacy` differs by flag, not engine (`src/cli/log.ts:583-618`). `db stats` has no alternate native row shape; native metrics rows are absent until extraction (`src/cli/db.ts:589-606`). `metrics` and console have no public success JSON envelope (`src/cli/metrics.ts:46-50`; `src/cli/console.ts:5-39`).

## 4. `job_id` visibility and opacity

Legacy `job_id` remains externally visible as `ps flat[].id`/inspect `job.id` and native summary `activation_id` (`src/cli/ps.ts:1012-1033,1123-1158`), `status jobs[].id`/`job.id` (`src/cli/status.ts:317-327,371-380`), human feed/log ids and log JSON `job_id` (`src/cli/feed.ts:568-590`; `src/cli/log.ts:604-632`), forensic `correlation.job_id` (`src/specialist/forensic-events.ts:121-138`), console rows/details (`src/cli/console/runtime.ts:301-345`), db stats `job_id` and benchmark `executor_job_id/reviewer_job_id` (`src/cli/db.ts:579-605,804-833`), result `job.id` plus startup `job_id` (`src/cli/result.ts:388-424,430-451`). A native row normally places `act:<core>` in those slots; a native attempt input `att:<core>:<n>` is mapped back to `act:<core>` storage (`src/cli/result.ts:108-129,499-505`). Metrics explicitly forbids opaque ids as labels (`src/specialist/forensic-events.ts:158-170`).

The value is **not opaque to all consumers**: feed cursor parsing assumes the id contains no colon (`src/cli/feed.ts:242-250`); result regex-parses `act:`/`att:` and splits colon refs (`src/cli/result.ts:108-129,170-182`); ps/status/console perform prefix matching (`src/cli/ps.ts:1036-1041`; `src/cli/status.ts:302-304`; `src/cli/console/runtime.ts:1031-1033`); console truncates display ids to 8 characters (`src/cli/console/theme.ts:217-225`); feed/log/db use lexical job-id tie-breaks/sorts (`src/cli/feed.ts:633-638`; `src/cli/log.ts:565-570`; `src/cli/db.ts:833-833`). Status: **ADAPTER_NEEDED**, chiefly for `feed --from` and visually ambiguous console ids.

## 5. Error and exit envelopes — preserve inconsistencies

| surface | actual error/no-data behavior and exit |
|---|---|
| `ps` | Inspect miss: JSON stdout `{error}` or human stderr text, exit 1 via `process.exitCode`; unknown flag throws to global fatal logger. Follow exits 0 on EPIPE, 130 on SIGINT, 143 on SIGTERM (`src/cli/ps.ts:1042-1049,1287-1301`; `src/index.ts:1466-1472`). |
| `status` | Parse errors: colored stderr text + exit 1. Job miss: JSON stdout `{error}` or human `fail(...)` on stdout, then exit 1. Other throws use global fatal text (`src/cli/status.ts:251-261,302-312`; `src/index.ts:1466-1472`). |
| `feed` | Missing job/no DB is a human stdout message or empty JSON stream and exit 0; follow completion messages are stderr only in human mode and still exit 0 (`src/cli/feed.ts:526-544,871-888,1028-1035`). Invalid/unknown options are largely ignored by the parser rather than enveloped (`src/cli/feed.ts:445-482`). |
| `log` | Parse/no-DB/client failures are plain stderr (plus usage for parse) and exit 1; no matches is stderr and exit 0; forensic read failures emit stderr NDJSON `{ts,component,op,repo,errorClass}` and continue; SIGINT/SIGTERM follow resolves normally, exit 0 (`src/cli/log.ts:476-515,578-600,650-662`). |
| `forensic` | Parse/DB errors throw to global stderr `[specialists] [ERROR] Fatal error: ...`, exit 1; no rows is empty stdout, exit 0 (`src/cli/forensic.ts:7-75`; `src/utils/logger.ts:7-18`; `src/index.ts:1466-1472`). |
| `metrics` | Parse/DB errors use the same global fatal text/exit 1; success writes exposition bytes directly and exits 0 (`src/cli/metrics.ts:8-50`; `src/index.ts:1466-1472`). |
| `console` | Recoverable internal failures emit stderr NDJSON base `{ts,component,view,op,exitCode,durationMs,errorClass}` plus optional `step,beadId`, usually without changing exit status; SIGINT/SIGTERM resolve normal exit 0; uncaught failures use global fatal text/exit 1 (`src/cli/console/log.ts:44-66`; `src/cli/console.ts:19-38`; `src/index.ts:1466-1472`). |
| `db` | Help exits 0. Setup/backfill noninteractive refusal is plain stderr + exit 1. Unknown subcommand is plain stderr plus help on stdout + exit 1. Parse/DB failures throw to global fatal text + exit 1. `stats --format json` has no JSON error envelope (`src/cli/db.ts:128-145,870-923`; `src/index.ts:1466-1472`). |
| `result` | Every runtime JSON success/error uses `{job,output,startup_context,error}`; semantic failures/not-found/running-without-output/timeout exit 1 with that stdout JSON or plain/colored human stderr. Running/waiting with a persisted output exits 0. Parse-time errors are plain stderr + exit 1 (`src/cli/result.ts:131-200,430-451,580-831`). |

## Byte-compatibility requirements found

1. **`sp metrics` Prometheus text — `BYTE_COMPATIBLE_REQUIRED`**: the source explicitly records a byte-equivalence gate and byte-format invariant (`src/specialist/live-aggregates.ts:21-27`; `src/specialist/prometheus-projection.ts:1-13`).
2. **`sp forensic` raw NDJSON event lines — `BYTE_COMPATIBLE_REQUIRED`**: the CLI writes persisted `event_json` directly rather than reserializing it (`src/cli/forensic.ts:65-75`).
3. **`sp result` human stdout body and stderr telemetry/footer split — `BYTE_COMPATIBLE_REQUIRED`**: stdout concatenates startup/payload blocks and stored output, while the metrics/waiting footer is written separately to stderr (`src/cli/result.ts:458-479,761-767,811-818`).

All other audited success formats are **`SEMANTIC_EQUIVALENT_OK`**, subject to the exact key names, event ordering, null/omission rules, and inconsistent error/exit envelopes documented above.
